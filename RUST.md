# Rust rules

Binding for every crate in this workspace: new code, and code ported from C/C++. Most rules are enforced
by the workspace config (`Cargo.toml` `[workspace.lints]`, `clippy.toml`, `rustfmt.toml`, `deny.toml`,
`rust-toolchain.toml`). The rest are review rules; a change that breaks one is not done.

The code is a GPU driver stack: it talks to the kernel through ioctls, shares memory with the GPU and with
other processes, and is loaded into arbitrary Android apps through C ABIs. A bug here corrupts someone
else's process, hangs the GPU or leaks kernel objects. The rules follow from that.

## 1. Crate layout: where unsafe may live

- Code is split by what it is allowed to do:
  - **`*-sys` crates**: raw bindings only. Generated by `bindgen` from the pinned upstream header
    (Mesa, open-gpu-kernel-modules, Android NDK/HAL headers), never hand-typed when a header exists.
    No logic.
  - **Boundary crates** (`rm`, the FFI export layer of each component): the only places with `unsafe`.
    They turn raw pointers, ioctls, mappings and C callbacks into safe Rust types.
  - **Logic crates**: `#![forbid(unsafe_code)]`. Encoders (push buffers, QMDs, descriptors, image
    layouts), parsers, state machines, policy. Most code belongs here.
- If logic needs `unsafe`, the boundary is missing an abstraction: add a safe API to the boundary crate
  instead of opening unsafe in the logic crate.
- One crate per component (`nvkmd-rm`, `hal`, `gralloc`, `codec2`, …). Shared code goes into a shared
  crate, not copies.

## 2. Unsafe

- Every `unsafe` block holds **one** unsafe operation and is preceded by `// SAFETY:` stating which
  invariant the operation needs and why it holds *here* (not "caller guarantees", unless this is an
  `unsafe fn` whose `# Safety` section says so). Enforced: `undocumented_unsafe_blocks`,
  `multiple_unsafe_ops_per_block`.
- Every `unsafe fn` and `unsafe trait` has a `# Safety` doc section listing the caller's obligations.
  Unsafe operations inside an `unsafe fn` still need their own block (`unsafe_op_in_unsafe_fn`).
- **A safe function is sound for every input.** If some argument value would cause UB, the function is
  `unsafe` or it checks and returns an error. "Safe if used correctly" is a bug.
- `unsafe impl Send/Sync` needs a SAFETY comment naming what makes cross-thread use sound (who owns the
  pointee, which lock guards it). A type holding a raw pointer is neither `Send` nor `Sync` until argued.
- No `transmute`. Byte views of wire structs go through `zerocopy` derives (`FromBytes`, `IntoBytes`,
  `KnownLayout`, `Immutable`); pointer casts use `.cast()`, `.cast_mut()`, `ptr::from_ref`.
- No `static mut`. Globals are `OnceLock`/`LazyLock`/atomics, and only when the interface forces global
  state (a C entry point with no context argument).
- `unsafe` added for speed needs a measurement in the commit message (before/after, idle GPU, workload).
- Unsafe code is exercised by Miri (logic without real syscalls) and by host tests under AddressSanitizer
  (FFI and syscall paths). A boundary module without such a test is not done.

## 3. Memory the GPU or another process can see

- **Never create `&T` or `&mut T` to memory that the GPU, the kernel or another process may write while
  the reference lives** (mapped VRAM/BAR1, GPFIFO/USERD, semaphores, notifiers, shared dma-buf
  mappings). That is UB regardless of what the hardware does. Wrap each mapping in an owning type
  (`Mapping`, `Userd`, …) whose accessors use `ptr::read_volatile`/`write_volatile` or atomics, check
  the offset against the mapping length, and take the offset as a typed value.
- Memory ordering against the device is explicit: every fence (`atomic::fence`, `compiler_fence`, an
  arch store fence before a doorbell write to write-combined memory) carries a comment citing the
  contract it implements (public header/manual section, or the measured driver behaviour it matches).
  No ordering is "probably fine".
- Mapping type (cached, uncached, write-combined) and placement (VRAM/sysmem) are part of the type or
  an explicit enum argument, never an implicit default.
- Unmapping and freeing happen in `Drop` of the owning type, after every borrow of the mapping has ended
  (the borrow checker should prove this, so accessors borrow the mapping).

## 4. FFI boundaries (C ABI exports, C/C++ callbacks)

- **No panic crosses an FFI boundary.** Every `extern "C"` function and every callback handed to C runs
  its body inside one shared guard (`ffi::guard`) that catches unwinds, logs the function name and panic
  message at error level, and returns the interface's most specific failure value (`VK_ERROR_DEVICE_LOST`,
  `-EIO`, `C2_CORRUPTED`, …). The object involved is marked failed, and later calls on it fail the same
  way instead of touching inconsistent state. Interfaces with no error return abort with the message.
  The release profile keeps `panic = "unwind"` so the guard works.
- Validate every pointer from C once, at entry: null, alignment, length. Then convert to a reference or
  slice whose lifetime ends with the call. Logic code never sees raw pointers.
- Each exported function documents ownership in its doc comment: who allocates, who frees, how long
  pointers stay valid, whether it may be called concurrently. Handles given to C are
  `Box::into_raw` of a Rust type (opaque to C) and come back through one function per type that checks
  for null; the matching `Box::from_raw` exists exactly once, in the destroy entry point.
- `#[repr(C)]` types come from `bindgen`. Where Rust defines a type C also reads, compile-time asserts pin
  size, alignment and every field offset (`const _: () = assert!(…)`) against the C header values, and an
  ABI test compiles the real header and compares.
- Strings from C are `&CStr`; never assume UTF-8, never `from_utf8_unchecked`.
- C++ interfaces (Codec2, HIDL mapper) go through `cxx`. The C++ side is the minimum the interface
  forces: no logic, no ownership decisions, no error policy.
- Exported symbol lists are explicit (version script or `#[unsafe(no_mangle)]` on exactly the ABI
  functions) and checked by a test against the expected list. Nothing else leaks out of a cdylib.

## 5. Types

- **Distinct quantities get distinct types.** GPU VA, CPU address, byte offset, byte size, page count,
  RM handle, class id, engine id, fence value: newtypes, not bare `u32`/`u64`. Arithmetic between them
  is defined only where it means something (`GpuVa + ByteSize -> GpuVa`).
- **Make invalid states unrepresentable.** Enums instead of bool parameters and magic numbers; typestate
  or an owning wrapper where lifecycle order matters (allocated → mapped → bound); a constructor that
  validates instead of a struct with public fields that callers may fill wrong.
- Values arriving from outside (kernel status, ioctl output, Vulkan enums from apps, gralloc handles from
  other processes, bitstream fields) are converted with `TryFrom` into our types at the boundary. An
  unknown value is a named error, never a default.
- `match` on our own enums is exhaustive: no `_ =>` arm, so a new variant forces every site to be
  reviewed (`wildcard_enum_match_arm`).
- Hardware constants and method/field encodings are named constants or typed builders with a citation
  (header file:line, class/method name). No hand-written shifts and masks in logic code.
- Every kernel or GPU object has an owning type whose `Drop` releases it. When teardown order matters,
  it is written out in one explicit `Drop` (or a `shutdown(self)` method), never left to field declaration
  order. `Drop` does not panic; a failed release is logged at error level with the object and status.

## 6. Integers and arithmetic

- No lossy `as`. Widening uses `From`/`u64::from`; narrowing uses `try_from` and handles the error.
  Enforced by `as_conversions` and the cast lints; a remaining `as` needs `#[expect(…, reason = …)]`
  saying why it cannot lose information or why truncation is the specified behaviour.
- Sizes, offsets, counts and addresses that come from outside use `checked_*` and return an error on
  overflow. `wrapping_*` only where the hardware or protocol wraps (fence counters, ring indices), with
  a comment saying so.
- `overflow-checks = true` in every profile, release included: a silent wrap in a size computation is a
  memory-safety bug in the GPU's address space even when Rust's own memory stays safe.
- Indices derived from external input use `.get()` and return an error. Indexing with `[]` is for
  indices the code itself proved in range.

## 7. Errors, panics, logging

- Libraries return `Result<T, Error>` with one error enum per crate (`thiserror` derive). Each variant
  names the operation and carries its context (ioctl, class, handle, raw status, size). Where the user
  can fix it (missing device node, driver version mismatch, unsupported GPU), the message names the
  remedy. No `anyhow`/`Box<dyn Error>` in library APIs; fine in test and tool binaries.
- **No silent fallbacks.** No `unwrap_or_default()`, `.ok()`, `let _ =` or `if let Ok` that throws away a
  failure the caller should know about. If degrading is intended, it is an explicit, logged decision in
  one place with the reason.
- No `unwrap()` outside tests. `expect("…")` only for invariants the surrounding code establishes, and
  the message states the invariant ("queue map holds every created queue"), not the symptom.
- No `todo!`, `unimplemented!`, `dbg!`, `println!`/`eprintln!` in library code. An unsupported feature
  returns a named error; output goes through `log` (Android logger backend on device, tag per component).
- Logging on per-frame or per-submit paths is off by default (debug level, or behind a runtime flag);
  errors are always logged.

## 8. Concurrency

- Prefer ownership and message passing to shared mutable state. Shared state sits behind one `Mutex`
  per object; the lock order between objects is documented in the module header, and no lock is held
  across a blocking ioctl or a call back into C unless the interface requires it (then say so).
- A poisoned mutex is a fatal error for that object (the panic guard already marked it failed), never
  `into_inner()`-and-continue.
- Every atomic `Ordering` has a comment saying what it synchronises with. `Relaxed` only for counters
  and statistics that order nothing.
- Lock-free structures and custom synchronisation get `loom` tests.
- Races are fixed by construction. A fix that only makes a window smaller (sleep, retry, poll loop) is not
  a fix.

## 9. Dependencies and toolchain

- Toolchain pinned in `rust-toolchain.toml` (stable, plus a dated nightly only for Miri, fuzzing and
  sanitizers). Edition 2024.
- `Cargo.lock` committed; dependencies vendored (`cargo vendor`) so builds are offline and reproducible.
  `build.rs` never touches the network and never reads outside the workspace and the pinned sources.
- Few dependencies, each justified in the commit that adds it (what it does, why not std or ten lines of
  our own, maintenance state). Preferred: `rustix` for syscalls/mmap/ioctl plumbing (fewer raw `libc`
  calls), `zerocopy`, `bitflags`, `thiserror`, `log`, `cxx`, `ash` (Vulkan types). `cargo deny check`
  passes: licenses, advisories, bans, sources.
- Targets: `x86_64-linux-android`, `i686-linux-android` (bionic), plus the host target for tests. No
  glibc-only API in code that ships to the guest.

## 10. Style and documentation

- `rustfmt` default style (the config only pins the edition). `cargo clippy --all-targets -- -D warnings`
  clean with the workspace lint set.
- Lints are never silenced with `#[allow]`. Use `#[expect(lint, reason = "…")]` at the narrowest scope;
  the reason states why the lint is wrong here.
- Every module starts with a doc comment: what it owns, what it must not do, its threading and locking
  model. Every public item has a doc comment. Comments explain *why* and cite public sources (Mesa
  file:line, open-gpu-kernel-modules, NVIDIA class headers, Android source); they do not narrate history
  or describe what the next line does.
- Names follow the Rust API guidelines. Short functions are a consequence of clear structure, not a
  line-count rule; split when a function mixes levels (validation, encoding, submission).
- Macros only for tables and repetitive declarations, never to hide control flow or unsafe.
- Every source file starts with `// SPDX-License-Identifier: MIT` (generated bindings carry their header's license).

## 11. Testing

- Logic is written so it runs without a GPU: encoders and parsers are pure functions tested against golden
  bytes (captured from the reference implementation or derived from the public spec, with the source
  named in the test).
- Hardware tests are separate, marked, and select the GPU by PCI vendor/device id, never by a `/dev/dri`
  node path.
- Every parser of untrusted input has a `cargo fuzz` target that runs in CI for a fixed time: bitstream
  headers (H.264/HEVC/VP9/AV1), gralloc handles and buffer descriptors from other processes, ioctl output
  we interpret, AHB/ANB descriptors.
- Boundary crates: Miri on everything that does not issue real syscalls, ASan host runs on the rest, ABI
  tests on every exported struct and symbol list.
- A bug fix comes with the test that failed before it.

## 12. Porting C/C++ to Rust

- **Port behaviour, not syntax.** No transliterated C inside Rust: no integer error codes, out-parameters,
  manual length bookkeeping or pointer arithmetic past the boundary layer. The C shape stays at the ABI.
- **The first port is behaviour-identical.** Same exported symbols and struct layouts, same ioctl sequence,
  same bytes to the GPU on the same input. Verify by differential tests: run the C and the Rust
  implementation on the same captured inputs and compare outputs (push-buffer bytes, ioctl traces, image
  layouts, returned values). Improvements and bug fixes go into separate later commits, each with its
  own test and stated reason. A C bug found while porting is reported and fixed in its own commit, not
  silently carried over or silently fixed.
- Until the Rust version passes the component's gate, both builds stay selectable at build time so A/B
  is one switch. When it passes, the C code is deleted in the same series. No dead copies.
- Port module by module with the boundary tests first: a port whose FFI shim has no ABI test is not
  started correctly.

## Gate (every change)

```
cargo fmt --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
cargo deny check
cargo +nightly-2026-10-24 miri test -p <crates without syscalls>
```

plus the component's own checks (ABI/symbol tests, fuzz smoke, differential tests for ports).

## Existing code

These rules apply in full to new crates and ports. Rust written before this standard is not a reference
for new code, and gets no exemption for being old. When such a crate joins the workspace:

- It uses the workspace lints like every other member. Each lint it still violates is listed once, at the
  top of its `lib.rs`, as `#![expect(clippy::…, reason = "pre-standard code; cleanup tracked")]`. That
  list is the crate's debt ledger: it never grows, and `#[expect]` turns an entry into an error once the
  lint stops firing, so a cleanup has to delete the entry.
- A change that touches an item brings that item up to the standard. Dedicated cleanup passes shrink the
  ledger lint by lint.
- Unsafe in such a crate gets its SAFETY comments and one-operation blocks before anything else, because
  those are the soundness arguments the rest of the review depends on.
